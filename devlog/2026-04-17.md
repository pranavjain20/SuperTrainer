# Apr 17, 2026 — Bug Fixes: Nav, Voice Pipeline 404, Plan Polish

## What Got Fixed

Four root-cause fixes across the stack, all surfaced by hands-on phone testing.

### 1. "Back to Home" navigated back, not home

`mobile/app/recording/[sessionId].tsx`. The button after ending a session was wired to `router.back()`, which pops the stack. Trainers mostly enter recording from a client profile's "Start Session" button — so "Back to Home" dropped them on the client profile, not home. Switched to `router.replace("/")`. The ended session is also cleared from the stack, so system back-gesture from home can't return to a done session.

### 2. Voice pipeline 404 — hallucinated Sonnet model ID

`backend/app/services/parser.py`. `DEFAULT_MODEL` was `claude-sonnet-4-6-20250627` — a fabricated dated suffix. Sonnet 4.5 dropped Sep 29, 2025, so a June 2025 Sonnet 4.6 is impossible. Anthropic returned 404, voice clips processed but produced no exercise cards. Fix: alias `claude-sonnet-4-6`. Also DRY'd `plan_parser.py` to import `DEFAULT_MODEL` from `parser.py` — one source of truth.

Zero tests caught this because every call site mocks the SDK. Added two defensive layers:

- **`backend/app/services/model_health.py`** — `ACTIVE_MODELS` registry and a `verify_active_models()` coroutine that pings each model with a 1-token request on FastAPI startup (via `lifespan`). A 404 raises `RuntimeError` before the server accepts traffic. Skips silently when `ANTHROPIC_API_KEY` is unset so tests and keyless dev envs still boot.
- **`backend/tests/test_smoke_models.py`** — parametrized real-API smoke test over `ACTIVE_MODELS`, marked `pytest.mark.smoke`, excluded from the default `pytest` run via `pytest.ini` `addopts = -m "not smoke"`. Run explicitly with `pytest -m smoke`.

Railway's deploy process runs `uvicorn`, which runs the lifespan — so the startup ping is the real guardrail. The smoke test is a backstop for explicit CI/pre-deploy invocation.

### 3. Plan creation polish — weight truncation, list not refreshing, date shift

Three related fixes to the plan creation flow:

**Weight field truncation.** `mobile/app/plans/form.tsx`. Layout was three columns (`sets: flex:1 / reps: flex:2 / weight: flex:2`), which cut "10kg, 12kg, 14kg" down to "14k". Switched to fixed-width 64px centered Sets and Reps chips plus a `flex:1` multiline left-aligned Weight field. Long weight lists now wrap instead of truncating. Sets/Reps numerals sit on the same row as Weight for a compact chip look.

**New plan didn't appear on Plans tab after save.** `mobile/src/hooks/usePlans.ts`. Tracked through three rounds of investigation — backend log showed the POST succeeded, a GET fired with 200, plan was in the DB, but the UI still showed old data. Root cause: `queryClient.refetchQueries` defaults to matching only *active* observers, and the form is a root-stack screen pushed over the tabs — the parent client profile's observer wasn't being reached across that navigation boundary. Rewrote all three mutation hooks (`useCreatePlan`, `useUpdatePlan`, `useDeletePlan`) to write the server response directly into the cache via `setQueryData` (prepend on create, map-replace on update, filter on delete), with `invalidateQueries` as a backstop. UI updates instantly — no refetch round-trip, no dependency on which observer is currently active. This is the React Query-recommended pattern for create-and-list flows.

**Date shift.** `mobile/src/utils/dates.ts`. `formatPlanDate("2026-01-31")` parsed as UTC midnight, then `toLocaleDateString` rendered it in EST, producing "Jan 30, 2026" — one day earlier. Fixed by appending `T00:00:00` to anchor it to local midnight, matching how `form.tsx` already loads these dates.

### 4. Plan set rendering — "Lunges shows 6 sets that don't make sense"

`mobile/src/utils/plans.ts` (new). Live testing on Jake's profile: the parser emitted `sets=6` with only 3 weight values for a Lunges plan. The old expansion code silently padded the missing slots with the first array value, rendering "12kg×12, 14kg×14, 16kg×16, 12kg×12, 12kg×12, 12kg×12" — nonsense data that looked like real data. Meanwhile Squats with 4 identical sets rendered "10kg×8, 10kg×8, 10kg×8, 10kg×8" — correct but redundant.

Extracted the rendering into a `formatPlannedSets` utility with two rules:

1. **Collapse uniform sets.** When weight and reps are both single values, render as `"N × weight×reps"`. `"4 × 10kg×8"` is clearer than four comma-separated repeats.
2. **Trust the arrays over the sets field.** When weight or reps varies, use the array length as the true set count. If the parser says 6 sets with 3 weight values, render 3 sets — the data we actually have. No silent padding.

Added `src/utils/__tests__/plans.test.ts` with 9 cases covering uniform collapse, single set, varying weights, varying reps, array-trumps-sets conflict, weight-only, reps-only, empty, and varying-weight-no-reps. All pass.

## Key Insight — React Query refetch across nav boundaries is fragile

The plan-list-not-refreshing bug was the hardest. Two false starts before root cause:

- Logs showed a GET firing without `?limit=20` even though the only `getClientPlans` caller passes `{limit: 20}` — suggested a phantom caller, but grep found only one. That GET was actually coming from the `refetchQueries` call running *some* queryFn, but not hitting the active observer's `useClientPlans`.
- Thought it might be a queryKey mismatch or stale closure — checked both, ruled out.

The real issue: `refetchQueries` with default `type: "active"` doesn't reliably match observers on a parent screen when mutation fires from a pushed screen. Writing the server response directly via `setQueryData` bypasses the match entirely — the cache update fires a re-render on every observer of that key, no exceptions.

Saved as a feedback memory for future React Query work on this codebase.
