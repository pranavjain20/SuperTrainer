# Day 5 (Phase 2a) — Feb 26, 2026

*The session recording screen. First time building something that feels like the actual product — a trainer taps record, speaks, stops, and audio is captured. Day 6 sends it to the backend.*

---

## What got built

The recording workspace: the screen where a trainer records voice clips during a session. Header shows client name, session time, status badge. Empty timeline area (Day 6 fills this with exercise/observation cards as they come back from the backend). Bottom bar with an animated record button.

5 new files. `useVoiceRecorder.ts` handles the full recording lifecycle — request mic permission on first tap, configure audio mode, create expo-av recording at 44kHz/128kbps AAC (m4a format matching what the backend expects as `audio/mp4`), track duration via interval, stop and capture the file URI. `RecordButton.tsx` is an 80px circle that springs to 1.25x when recording starts, with a pulse ring that expands and fades behind it. Haptic feedback on tap. `recordingStore.ts` is a Zustand store that shares recording state between the recorder and the tab layout — needed for navigation guards. `useSession.ts` is a simple single-session query hook. `[sessionId].tsx` ties it all together.

Session tab got a real session list (replaced the placeholder). Home screen session taps now navigate to the recording screen. Three modified files for routing and navigation.

The navigation guard came from testing on phone — I noticed you could tap away to another tab mid-recording with no warning. Built a system where the tab layout checks `isRecording` from the Zustand store and intercepts tab presses: "Keep Recording" or "Stop & Leave." Same pattern on the back button within the session screen. The recording actually stops before navigation happens.

## What went right

This session went noticeably smoother than previous days. The difference: during planning, the backend contract was mapped out explicitly — what endpoint the audio goes to (`POST /sessions/{id}/voice-clip`), what format it expects (m4a as audio/mp4), what's already built on mobile (`processVoiceClip()` in `voice.ts`). So when building the recorder hook, there was no guessing about output format or what Day 6 needs. Everything was built to plug in cleanly.

The result: things worked correctly on first deploy. Which meant the feedback loop was entirely about how things *look*, not whether they *work*. Bigger text, bolder status badges, smoother animation curves, more visible pulse ring — all of that is satisfying to iterate on when you're not also debugging broken functionality underneath.

Two compatibility issues hit and got solved quickly. Reanimated v4 has a Worklets version mismatch with Expo Go (0.7.4 vs 0.5.1) — rewrote RecordButton to use React Native's built-in Animated API instead. The expo-av config plugin breaks Expo Go's native runtime — dropped it (expo-av works fine without the plugin in Expo Go, permissions prompt happens at runtime).

## Reflections

Correctness before aesthetics changes the entire feel of a session. When the code works right — the recording starts, the animation fires, the permission dialog appears, the file URI shows up in logs — then tweaking how it looks is fun. You're polishing something that works. When the code is broken underneath, every visual tweak feels like rearranging furniture in a house with a cracked foundation. The planning mode investment (mapping the backend contract, understanding what Day 6 needs) paid for itself by making the whole afternoon productive instead of frustrating.

The expectation going forward: this kind of backend-awareness should happen automatically, not because it was explicitly requested. Build from reality (what the backend actually sends and expects), not from types alone. The types describe the interface; the backend describes reality.
