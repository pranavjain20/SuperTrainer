## What Got Built

The client profile screen — tap a client from the list, see their full profile with three tabs: Overview, Sessions, Plans.

Overview shows goals as colored pills and injury history as red pills. Sessions tab has expandable cards — tap one and it lazy-loads the entries for that session. Exercise cards render as set tables (Set / Reps / Weight / RPE / Notes), observation cards render between exercises with a left-border accent. Plans tab shows plan text in numbered cards.

The set table only shows the Notes column when at least one set actually has a note. Observation cards appear in sequence order — they can show up before the first exercise, between exercises, or after the last one, depending on when the trainer said them during the session.

Also rewrote Sarah Chen's seed data. The old seed had fake "form_notes" like "good depth, slight knee cave" and a single observation at the end about vibes ("motivated and coachable"). The new seed has per-set notes ("left glute felt tight", "cut short, felt dizzy"), a pre-session observation ("Sarah hasn't slept much, energy below baseline"), and a mid-session observation between exercises ("energy levels even lower after goblet squat and Romanian deadlift"). Data that a real trainer would actually record.

## The Hard Part

This was the most frustrating day of the project so far. Not because the work was hard — the React Native code is straightforward. Because I spent most of the day fighting Claude on correctness.

The TypeScript `SetData` interface had a `set_number` field. The backend doesn't have that — seed data uses `"set"`, voice pipeline has no set number at all. Claude built the display from the TypeScript types instead of reading what the backend actually returns. The set numbers didn't show. The weights didn't show. RPE was hidden. Notes were in the wrong place.

Then the note hierarchy. Claude displayed `form_notes` as a separate "Notes" section below the set table. Then as inline italic text under the exercise name. Then tried "Trainer Notes." None of these are real concepts. A trainer doesn't say "good depth, slight knee cave" as a separate annotation after an exercise. Notes go per-set in the table. Observations are independent entries in the timeline that appear between exercises when the trainer records them. That's it — two things, not three.

It took probably 8-10 iterations to get the data display right. Each time I had to catch the mistake, explain why it's wrong, and wait for the fix. The frustrating part: if Claude had just read the backend seed data first — looked at how `_seed_sarah()` constructs entries, what keys the sets actually have, how sequence_order places observations between exercises — it would have known exactly what to build. The PRD describes it. The build plan describes it. The backend implements it. All the context was there. It just wasn't used.

## The Distinction That Matters

Not being beautiful is different from not being right.

Making a set table look sophisticated — choosing the right font weights, spacing, colors — that's iterative and subjective. I don't have strong frontend instincts yet, so I can't always articulate what "looks good." That's a collaboration problem, and it's partly on me.

But displaying data that doesn't exist (`set_number`), inventing UI concepts that don't match the product (`form_notes` as a separate section), not reading the backend to understand what the frontend should show — those are correctness failures. They waste time and tokens, and they're entirely avoidable. The fix isn't "try harder" — it's "read the backend first, every time."

## Reflections

Today was a reality check on how different backend and frontend work are with AI. The backend phases moved fast and felt solid — there's a clear spec, clear tests, clear right answers. Frontend is messier. The "right answer" depends on understanding the product deeply enough to know what data matters and how it should flow. Claude didn't bring that understanding today. It treated the frontend as a separate thing from the backend instead of reading the backend to figure out what to build.

Part of the visual iteration problem is on me — I'm new to frontend and can't always explain what I want. I don't know the vocabulary for "make this look sophisticated" in a way that translates to specific CSS properties. That's a skill I need to develop. But the correctness stuff — that's not a communication problem. That's a "read the codebase" problem. And it has to be solved before we get to more complex screens.

The lesson is already in `tasks/lessons.md`, but it needs to become instinct: before building any frontend display, read the backend service that creates the data, the schema that serializes it, and the seed that demonstrates it. Build from reality, not from aspirational types.
