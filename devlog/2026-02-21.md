## The thing nobody tells you

When I started this project, I genuinely thought I'd have an AI app built in a weekend. Monday morning, done. I have an engineer who knows all this shit, who can build anything I tell him to build. How hard could it be?

It turns out: incredibly hard. Not the coding — the thinking. Going through every single workflow. What does a trainer see when they open the app? OK, what data drives that screen? Where does that data come from? How does the voice pipeline process it? What happens when the audio is bad? What happens when the trainer says "sets 2 through 4 at 85 kilos" — how does the parser handle that? Every question branches into five more questions, and each of those branches into five more.

The PRD alone took an entire day. Not because writing is slow, but because every feature requires walking through every decision — from the first design choice a user sees to the most deeply technical implementation detail. Even for just three core features (voice capture, session timeline, The Brain), the spec document is massive. Every edge case, every data flow, every "what if" needs an answer before a single line of code gets written.

I'd read somewhere that if something can be vibe-coded in a weekend, you're not thinking big enough. That hit different this week. SuperTrainer can't be vibe-coded in a weekend, because there are hundreds of real decisions that need to be made if it's going to actually work for real trainers. And that's a good thing.

## The moment I stopped the build

At some point during the session, I realized something was off. The engineer was plowing through code — models, schemas, CRUD endpoints, tests — and I was just... watching. Reviewing after the fact. Approving things. Not learning anything.

And I stopped it. I said: when will I start learning? Because the whole point of this project isn't just to have a working app. The point is that I come out of this genuinely understanding AI — voice pipelines, RAG architectures, embeddings, conversational agents, all of it. If someone asks me how The Brain works, I need to be able to explain it from first principles, not just point at code someone else wrote.

So I changed the approach. The infrastructure and CRUD work can move fast — that's plumbing, and I don't need to write every line of it myself. But when we hit the AI phases (voice pipeline, transcript parsing with Claude, pgvector semantic search, The Brain), we slow down. I work alongside, not just review. I make the design decisions. I understand the trade-offs. Even if it takes twice as long.

This felt important. Not just for the project, but for me. I have an idea, I have an engineer, I can solve a problem — but I'm also genuinely curious and I want to learn. The moment the build started feeling like delegation instead of learning, I course-corrected. I think that instinct is worth remembering.
