## Understanding the architecture

Before building, I needed to understand something that confused me: if Deepgram only accepts 100 keyterms, why are we building a JSON file with 97 exercises and hundreds of fields? Aren't they the same thing?

They're not. The JSON file is the full exercise dictionary — unlimited, as detailed as we want. It's the single source of truth used by multiple systems: the Deepgram keyterm list is derived from it (top 100 terms extracted at runtime), the parser will fuzzy-match against it (Day 4), and The Brain will use it for domain knowledge (Phase 3). The 100-term limit is just one downstream consumer. The database itself has no size constraint.

This was a small but important moment — understanding how one file feeds into multiple systems at different phases. It's the kind of architectural thinking I want to get better at.

### You can't just say "make it the best"

This was the biggest, most painful lesson. My first instinct when starting the exercise research was to open Claude cloud and say something like: "I want to create the best possible exercise database. Do very deep research — journals, articles, textbooks — and make this as good as the world's best JSON document about exercises."

I didn't specify what kind of research. I didn't specify what to look into. I didn't specify how Claude should approach it or what output format I wanted. I just said "make it the best" and thought that would be enough for a smart AI model.

It wasn't.

The context window expired. I had no idea what thinking Claude had done. I couldn't evaluate the output because I wasn't part of the process. I couldn't add my own judgment or intuition because I'd delegated the entire thing wholesale. And now I had a used-up context window and nothing to show for it.

This is the trap: because Claude has access to the internet and is incredibly knowledgeable, it's tempting to think that delegating everything to it will produce better results than doing it yourself. But that's wrong. This is not my statistics homework where AI gets a better grade than me. This is a real product with no rubric and no right answer. Just because Claude can scan the internet faster than me doesn't mean I should hand over the thinking.

### The methodology that actually worked

After wasting two hours on the "just make it great" approach, I figured out the right workflow — and it was completely different:

1. Ask Claude to do deep research on *one* exercise (Nordic Hamstring Curl)
2. Have Claude explain how it would research, what it would look into, how it would structure the output
3. Review the result together — back and forth on what to keep, what to remove, what the right level of detail is
4. Agree on a template: canonical name, aliases, category, primary muscles (anatomical names), secondary muscles, equipment, difficulty, common errors with coaching context. No research_notes (that belongs in RAG, not this JSON).
5. *Then* — and only then — parallelize. Give 15 different Claude instances 10 exercises each, all following the agreed methodology.

That's when things clicked. The difference: in the first approach, I delegated both the thinking and the execution. In the second approach, I owned the thinking (methodology, format, quality bar) and delegated only the execution. The AI works for me, not the other way around.

But it took the entire day to learn this. Two hours figuring out logistics, frying tokens on approaches that didn't work, getting context windows to expire before producing useful output. From a pure output perspective, I couldn't even finish the exercise file today. But from a learning perspective, I landed on a methodology I'll use for the rest of this project.

### Voice changes the dynamic with AI

I'm talking to Claude Code through voice transcription, and I noticed something important: I'm saying 50x more than I would type. When you type, you naturally edit yourself — you compress, you cut fluff, you front-load the important stuff. When you talk, you ramble. You tell stories. You bury the key point in the middle of a paragraph.

This matters because of how these models work. If I give Claude a very long prompt and the important information is in the middle, it gets less attention. This is the "lost in the middle" problem — models pay most attention to the beginning and end of long inputs. When I'm talking for minutes at a time, the critical instruction might be sentence 47 out of 60.

And it compounds: every long message I send to Claude Code takes up context tokens. That's space that could be used for code, for file reads, for actual work. If Claude doesn't get the important information because it's buried in a wall of voice-transcribed text, it might build something I don't want, or forget something I told it that I think is important. That might even explain why Claude sometimes seems to "forget" things I've told it — not because it can't remember, but because the information was buried in a long conversational message and didn't get the weight it deserved.

I don't have a perfect solution yet. But being aware of this changes how I should communicate: front-load the important stuff, keep prompts focused, be more intentional about what I say versus what I think out loud.

### Context windows aren't unlimited

Even with Claude Pro Max, context windows end. I learned this the hard way — mid-research, the cloud chat hit its limit and I lost all the accumulated context. I hadn't thought about context as a finite resource before. Now I know: be smart about it. Plan for it. Save intermediate outputs. Don't assume you can have one infinitely long conversation.

It's your product. There's a difference between the two, and I learned that difference today.

### The first spark (morning)

Before all the afternoon chaos, the morning planning session had its own important moment. I finally understood tool_use — how it turns Claude from a chatbot into a structured extraction system. You define a schema matching your database model, and the LLM fills it in like a form. The schema isn't generic; it's `SessionEntry`, built over ten days of Phase 1a work. That's domain knowledge encoded into the interface between AI and the system.

This answered the "ChatGPT wrapper" question I'd been carrying for weeks. Without tool_use, you'd call Claude and get text, then need a second parser to structure it. With tool_use, Claude *is* the parser. The intelligence isn't in the model — it's in the tool schema, the system prompt, the validation rules. It's the fact that I know a trainer says "5 sets of squats at 80 kilos, RPE 8, knees caving on the last two" and I know that means one exercise card with 5 set records, a weight field, an RPE field, and a form note. Claude doesn't know that by default. It knows because I told it — through a schema I designed based on a data model I built based on understanding how trainers actually work.

And this connects to bottom-up learning. If I'd seen tool_use in a YouTube video, I would've thought "cool, function calling" and moved on. But because I need it for something real — to parse trainer voice notes into my specific database structure — the concept is concrete. The questions come from the problem, the learning follows the questions. "What is tool_use?" becomes "how do I make Claude output structured data that matches a specific Postgres table I built?"

That curiosity was missing during the Phase 1a CRUD grind. It's here now.
