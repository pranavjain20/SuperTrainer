## What we planned

The voice pipeline has four pieces:

1. **Deepgram** — speech-to-text. Black box API. One clever trick: a 100-term cheat sheet of gym vocabulary so it doesn't transcribe "Romanian deadlift" as "remaining deadlift."
2. **Claude parser** — the brain. Takes transcript + session context, uses tool_use to output structured JSON matching our SessionEntry model. 80% of the engineering effort lives here.
3. **Validation layer** — post-processing. Fuzzy-matches exercise names to our canonical DB, normalizes "185 pounds" to 83.9 kg, expands "3 sets of 10" into 3 records, catches pain mentions.
4. **Voice clip endpoint** — glues it all together. Audio in, structured entry out, timing breakdown included.

Seven days. Days 2, 3, and 6 are collaborative (AI decisions). Days 1, 4, 5, 7 are more independent. I need to write 5-10 real trainer transcripts before Day 6.

## Reflections

This was a big day internally. Only an hour of work, but it rewired how I think about what I'm building.

**The ChatGPT wrapper question.** I've had this nagging thought for weeks: if my product is "voice in, AI parses it," am I just a wrapper? What's the difference between this and a weekend hackathon project? I didn't have a good answer. Today I got one, and it's specific: **tool_use**.

Tool_use is how you make an LLM output structured data instead of prose. You define a schema — the exact fields you need, in the exact shape your database expects — and the model fills it in like a form. Not text. Structured JSON. The schema isn't generic; it's `SessionEntry`, the model I built over the last ten days. Exercise cards, observation cards, set arrays, RPE, form notes, pain flags. That's domain knowledge baked into the interface between the AI and the system.

Without tool_use, you'd call Claude's API, get text back, and then need a *second* NLP layer to parse that text into structured data. Two points of failure. With tool_use, you skip that step entirely — the LLM *is* the parser, outputting directly into the shape your backend needs. You're not building a chatbot. You're building a structured extraction system where the schema encodes everything you know about the domain.

That's what makes it vertical AI. The domain knowledge isn't in the model — it's in the tool schema, the system prompt, the validation rules. It's the fact that I know a trainer says "5 sets of squats at 80 kilos, RPE 8, knees caving on the last two" and I know that means one exercise card with 5 set records, a weight field, an RPE field, and a form note. Claude doesn't know that by default. It knows it because I told it — through the schema I designed based on a data model I built based on understanding how trainers actually work.

I want to go deeper on this. Not just use tool_use — understand the mechanics, the prompt engineering that makes it reliable, the failure modes. This is the thing I'll be explaining in interviews when someone asks what makes this product intelligent.

**Bottom-up learning.** Everyone told me: you learn by building, not by studying first. College teaches the opposite — learn everything, then apply. I've heard this advice a hundred times. Today was the first time I actually *experienced* it.

If I'd encountered tool_use in a YouTube video or a docs page, I would've thought "cool, function calling, got it" and moved on. Abstract knowledge. But today I understand *why* it matters — I need Claude to output `SessionEntry`-shaped JSON because that's what my database expects, because that's what the mobile app will display, because that's what turns a trainer's voice note into a searchable workout log. The concept is concrete because I need it for something real.

And that's the thing — when you're building, the questions become real. Not "what is tool_use?" but "how do I make Claude output structured data that matches a specific Postgres table?" Not "what is fuzzy matching?" but "how do I make sure 'bench' resolves to 'Barbell Bench Press' in a 100-exercise database?" The questions come from the problem, and the learning follows the questions.

It's also just tough. There are real layers to this. It's not "call API, get answer." It's: how does the transcript get structured? How does that structure match the database? How do you handle corrections mid-sentence? How do you handle references to previous exercises? Each layer has decisions, and each decision requires understanding something I didn't know yesterday. That's what makes it not a wrapper — the layers of intelligence between "audio file" and "structured database entry."

**The first spark.** I only spent an hour on this today. But it flipped something. The CRUD phase was necessary — I know that — but it didn't make me curious. I was planning, reviewing, approving. Today I'm curious. I want to know how Deepgram's keyterm prompting actually changes transcription accuracy. I want to see what happens when Claude gets a messy transcript full of "uh"s and mid-sentence corrections. I want to understand what makes a system prompt good versus bad.

That curiosity is the thing I was missing during Days 4-8. It's here now. And I think it's going to compound — every concept I learn during the AI phases connects to the next one. Tool_use connects to prompt engineering. Prompt engineering connects to RAG. RAG connects to The Brain. Each piece builds on the last, and each piece is something I can actually talk about with depth.

One hour. First spark. The AI phase begins tomorrow.
