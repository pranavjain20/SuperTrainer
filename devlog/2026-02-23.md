## The thing about tool_use

I spent an hour today planning the voice pipeline. Just one hour — no code written, no tests, no commits. And it was the most important hour so far.

Here's what I used to think: if your product is "we take voice input and use an AI API to parse it," you're a ChatGPT wrapper. A weekend project. What's the moat? What's the difference between you and every other AI startup that's just bolting GPT onto a form?

Today I learned the answer, and it's embarrassingly concrete: **tool_use**.

Tool_use (or function calling) is how you make an LLM output structured data instead of text. You define a schema — "here are the exact fields I need: exercise name, sets, reps, weight, RPE, form notes" — and Claude fills it in like a form. Not prose. Not markdown. Structured JSON that matches your database model. You're not asking Claude to write a response; you're asking it to classify, extract, and structure information into a format you designed.

That's what makes it vertical AI. The schema isn't generic. It's `SessionEntry` — a model I built over the last ten days, with exercise cards and observation cards and set arrays and pain flags. The domain knowledge is in the schema: a trainer says "5 sets of squats at 80 kilos, RPE 8, knees caving on the last two reps" and the system needs to know that's one exercise card with 5 set records, a weight in kilograms, an RPE field, and a form note. None of that is obvious to a generic API call. All of it is obvious if you've designed the right tool schema and given Claude the right context.

If we just called the Claude API raw — send transcript, get text back — we'd need a second NLP layer to parse Claude's text into structured data. Two points of failure instead of one. Tool_use skips that entirely. The LLM *is* the parser, outputting directly into the shape our backend expects.

I want to go deeper on this. Not just use it — understand the mechanics, the failure modes, the prompt engineering that makes it reliable. This is the thing I'll be talking about in interviews.

## The pipeline, demystified

We broke the voice pipeline into four pieces:

1. **Deepgram** — the ears. Takes audio, returns text. Black box, minimal custom logic. One interesting trick: you can give it a "cheat sheet" of 100 terms it should listen for (exercise names, gym vocabulary). Deepgram calls this keyterm prompting. Without it, "Romanian deadlift" might come back as "remaining deadlift."

2. **Claude parser** — the brain. Takes the transcript and session context, uses tool_use to output structured exercise cards and observation cards. This is where 80% of the engineering effort goes. Prompt design, schema design, testing, iteration.

3. **Validation layer** — the cleanup crew. Fuzzy-matches exercise names to our canonical database ("bench" → "Barbell Bench Press"), normalizes units ("185 pounds" → 83.9 kg), expands shorthand ("3 sets of 10" → 3 individual set records), and catches pain mentions.

4. **Voice clip endpoint** — the glue. One API call: audio in, structured entry out, with timing breakdown so we know what's slow.

When you say it like that, it doesn't sound impossible anymore. Each piece is a service with clear inputs and outputs. Deepgram's output feeds Claude's input. Claude's output feeds validation's input. Validation's output matches our database schema.
