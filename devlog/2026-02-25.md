# Day 7 (Phase 1b) — Feb 25, 2026

*Phase 1b complete. 25 live scenarios, 100% accuracy, all exit criteria met. The voice pipeline works.*

## What got built

One deliverable today: a consolidated live accuracy test suite that measures the parser against everything we've built, produces hard numbers, and tells us whether Phase 1b is done.

`backend/scripts/test_pipeline_live.py` — 25 scenarios across four sections. Section A: 9 real trainer quotes from the recorded session (the clamshells, the squats with band, the energy observations). Section B: 6 synthetic patterns covering rules the real transcript didn't hit (RIR, batch recording, structured corrections). Section C: 5 observation attachment tests (set-specific pain, general complaints, temporal context). Section D: 5 adversarial edge cases designed to break things — ambiguous exercise references, noise-only transcripts, contradictory corrections, a made-up exercise name.

Each scenario has structured expected outputs. The runner scores results against expectations and produces an exit criteria scorecard at the end. Flexible scoring handles LLM non-determinism: when Claude attaches an observation to an exercise that's contextually correct but wasn't strictly required, the test accepts it instead of failing.

Results on first run: 100% parse rate, 100% exercise name accuracy, 100% set/rep accuracy, 100% weight accuracy. No prompt tuning needed. The adversarial cases all passed — Claude yellow-flagged the ambiguous reference instead of guessing, handled noise gracefully, corrected the contradictory rep count, parsed the dense multi-content clip into separate exercise + observation cards, and preserved the made-up exercise name exactly as spoken.

Two minor audit fixes: a bare `list` type hint on `_extract_parser_result` (now `list[Any]`), and a misleading docstring on `_build_modification_kwargs` that implied different behavior for "add" vs "correct" actions on form_notes. 683 tests still green.

# Phase 2 Day 1 — The Product Becomes Real

*First time seeing SuperTrainer on a phone. Four tabs, instant updates, and suddenly it's not just an API anymore.*

---

## What got built

Backend pre-work: a trainer-level sessions endpoint (`GET /api/v1/sessions`) with date filtering. The home screen needs "all my sessions for today" across all clients — the existing endpoint only served sessions under a specific client. Filters on `scheduled_for` or `started_at` matching the date, so ad-hoc sessions still show up. 8 new tests, 691 total backend tests green.

Mobile app from scratch: Expo SDK 54 project, four-tab navigation (Home, Clients, Brain, Session), NativeWind for Tailwind-style CSS, TanStack Query for data fetching, Zustand for local state. Root layout wraps everything in a QueryClientProvider. Each tab renders a placeholder screen with styled text.

Hit a wall with SDK versions — Expo Go on the App Store only supports SDK 54, but `create-expo-app` scaffolded an SDK 55 project. Took some back-and-forth to figure out: the fix was downgrading to SDK 54 and swapping `expo-audio` for `expo-av`. Everything else stayed the same. Easy upgrade path when Expo Go catches up.

NativeWind (Tailwind for React Native) configured in under 10 minutes — no issues. This was flagged as a risk in the plan ("30-min timebox, if it fights us, fall back to StyleSheet"). It didn't fight us.

## What I learned

This was the first time touching React, React Native, or Expo — any of it. The concepts that clicked:

- **Components are functions.** Props in, UI out. State changes trigger re-renders. That's the entire React mental model.
- **File-based routing.** Folder structure IS navigation. `_layout.tsx` files define how children render (tabs, stacks). `(tabs)` is a layout group that doesn't affect URLs. Same idea as Next.js.
- **Expo Go is a container.** It already has all the native modules baked in. My code runs inside it. Metro bundles my TypeScript and sends it over Wi-Fi. That's why I never touch Xcode.
- **Fast Refresh.** Edit a file, Cmd+S, phone updates in under a second. This is the development loop for the entire phase.

Wrote a comprehensive concepts doc (`concepts/phase-2-day-1.md`) covering React, React Native primitives, Expo architecture, file-based routing, NativeWind, TanStack Query, Zustand, and the SDK versioning issue.

## Reflections

Seeing the app on my phone changed something. Phase 1a and 1b were all backend — API calls returning JSON, test suites passing, numbers on a terminal. Important work, but abstract. Today, tapping between four tabs on my actual phone, changing text in VS Code and watching it appear on the screen a second later — that's when it felt real. Not "I have an API that processes voice clips" real. "I have an app on my phone" real.

And a few days after that, I'll be speaking into my phone and watching exercise cards build in real time. That's the product moment. Today was the first step toward it, and it felt like the beginning of something visible.

Also built the API client layer (plan's "Day 2" scope) — 23 TypeScript interfaces mirroring every backend schema, fetch wrapper with error handling, and 5 endpoint modules covering all backend routes. Staff engineer audit caught 11 route mismatches where the frontend assumed fully nested REST paths but the backend uses mixed nesting. All fixed before commit.

# Phase 2a Day 3 — The App Comes Alive

*Two screens pulling real data. The first time SuperTrainer looks like a product on a phone.*

---

## What got built

Before today, all four tabs were blank placeholder screens. The API layer and types existed but nothing rendered real data.

Now the app has two working screens pulling live from the backend.

**Home tab** — fetches today's sessions, shows them as cards with client names (resolved via client-side join), time, and smart status pills. Done shows green, In Progress shows blue, and upcoming sessions show a countdown — "In 45 min" in amber, "In 2h 30m" in gray. Both the sessions query and client list query fire in parallel; a loading spinner covers until both resolve.

**Clients tab** — fetches all active clients, displays them alphabetically in a searchable section list grouped by first letter. Each card has a deterministic colored initials circle (future profile pic slot), bold name, and a chevron. Search filters in real-time. Pull-to-refresh on both screens. Tapping a client navigates to a placeholder detail screen ready for Day 4.

Supporting infrastructure: date formatting utils (`formatTime`, `formatDayHeader`, `toISODateString` with local timezone), `useClients` + `useClientMap` hooks with 5-minute cache, `useTodaySessions` hook with client name join, three shared state components (Empty/Loading/Error). All four tabs now use consistent custom headers with safe area insets instead of the mixed nav bar approach. Splash screen switched from invisible Expo placeholder to solid brand blue.

12 files created, 10 modified. TypeScript clean, lint clean.

## The debugging gauntlet

Getting the phone to actually talk to the backend ate real time. The backend needed `python-multipart` installed, needed to run inside the virtual environment, needed `--host 0.0.0.0` to be reachable from the phone's network, and had a zombie process holding port 8000. Expo needed tunnel mode and `@expo/ngrok`. The app would load tabs but API calls silently failed — no obvious error, just empty screens.

Each issue was individually small, but stacked together they were disorienting. And test data had its own problems: sessions created with `datetime.utcnow()` landed on February 26 UTC when the local date was February 25. The countdown logic was correct but couldn't be visually verified — had to prove it with a standalone node script running 6 test cases.

## The iteration loop

The first version of each screen was functional but ugly. Over 8-10 rounds of feedback, the screens evolved: bigger names, card-based layouts with shadows, colored initials circles, smart countdown pills, consistent headers across all tabs, removal of confusing elements (raw goal tags that made no sense out of context), proper splash screen. The final result looks genuinely clean.

## Reflections

Frontend is a different muscle. On the backend, "create a client endpoint" has one right answer — the schema, the service function, the tests. On the frontend, "show the clients" has a hundred valid designs and you have to pick one. The biggest realization today: I'm not naturally good at articulating what I want visually. "Make it look better" is easy to say, hard to be specific about. I kept giving ambiguous instructions and then iterating when the result wasn't what I had in my head. That's not a bad process — it's literally how design works — but it was humbling to realize how much I was feeling my way through it.

The debugging was the hardest part emotionally. Backend and AI debugging, even when things break, I can follow the logic and understand what's happening. Frontend environment debugging — Expo tunnels, network binding, port conflicts — felt opaque. I was entirely dependent on Claude to diagnose things I couldn't even read. That powerlessness is uncomfortable, and it's something I want to close the gap on.

But the payoff: there's something fundamentally different about seeing your app on your actual phone with real data versus green test output. The visual feedback loop is addictive — I didn't even notice how much time had passed. The app is starting to feel like something real.
