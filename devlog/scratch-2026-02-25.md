## Trainer Insight: Language Varies by Experience Level (PRODUCT-CRITICAL)

From today's session with the trainer. Two connected insights:

1. **Client vs trainer speech is fundamentally different.** An athlete using the app solo would talk to it very differently than a trainer recording for a client. The system has to handle both.

2. **Even among trainers, experience level changes the language.** A trainer who just started vs 5 years vs 10 years vs 20 years will describe the same thing in completely different words. A new trainer might say "his back was rounding" while a veteran says "lumbar flexion under load." The Brain needs to be smart enough to understand both and get more accurate over time.

**Product implication:** During onboarding, we should ask trainers how long they've been training. This feeds into the parser/Brain's interpretation — not just as metadata, but to calibrate how it interprets shorthand and technical language.

**Bigger picture:** The system can't assume one level of vocabulary. It has to work for the new trainer who says "left side is weaker" AND the experienced trainer who says "left adductor activation deficit." Both mean the same thing. The Brain has to converge on the same understanding regardless of input sophistication.

## Concrete Build Decisions from Today's Session

These are NOT reflections — these are real things that need to be built/changed.

1. **RPE as per-set float field.** Add `rpe` (float, nullable) to each set dict in the sets JSONB. Parser recognizes "RPE X", "RIR X", "intensity X", "could do X more". Validation layer converts RIR→RPE using Zourdos scale (RPE = 10 - RIR, half-points for ranges). Accepts whole numbers and half-points (7.5, 8.5, 9.5). → Affects: schemas.py, parser.py, validation.py. Day 6-7 work.

2. **Equipment modification ≠ new exercise.** "Squats with red band" = set 3 of squats with equipment metadata, NOT a new exercise card. Modification stored as set-level metadata (e.g., `"equipment_note": "red band"`). Parser prompt needs explicit instruction about this. → Affects: parser.py prompt, maybe sets JSONB schema. Day 6.

3. **RIR→RPE conversion table (Zourdos scale).** RPE 10=RIR 0, 9.5=~0, 9=1, 8.5=1-2, 8=2, 7.5=2-3, 7=3, 6.5=3-4, 6=4, ≤5=5+. Store as utility function in validation.py. → Day 6-7.

4. **Trainer experience level in onboarding.** Add `years_experience` (int) and possibly `specializations` to trainer profile. Feeds into Brain interpretation layer. → Phase 3-4, but flag in PRD now.

5. **Parser test cases must span language sophistication.** Include both "left is tougher" and "left adductor activation deficit" style observations. → Day 6 test design.

6. **Natural messy speech is the design constraint.** Parser prompt cannot require structured input. Trainers will ramble, use shorthand, mix exercise data with observations in one clip. Convenience = adoption. → Parser prompt design on Day 6.

7. **Superset support.** Trainer says "superset squats and lunges" → two exercise cards linked by a `superset_group` ID on session_entry. Display grouped, not independent. Parser needs to recognize "superset X and Y" pattern. → Schema change (add superset_group to session_entries), parser prompt update. Day 6-7 or Phase 2.

8. **Catch-up / batched clips.** Default is one clip per set, but trainer may forget and batch: "bench press, first set 60kg 10 reps, second set 60kg 8 reps." Parser must create multiple sets from one clip. → Parser prompt + test cases, Day 6.

9. **Structured corrections.** Trainer naturally says "correction, change third set bench press from 12 kg to 8 kg." Parser maps this to modify_exercise_card with target_entry_id + target_sets. Also handle casual style: "actually that was 8 not 12." → Parser prompt + test cases, Day 6.

10. **Mid-session general observations ≠ per-set observations.** "Energy levels are lower now" is a general session-level observation, not attached to any exercise. Parser/Brain must distinguish between per-set observations (attached to an exercise card) and general session observations (standalone observation card). → Parser prompt, Day 6.

## The Real Market Insight: Trainers Don't Know What's Possible (CRITICAL REFLECTION)

This came from a live conversation with the trainer during the session. This is the core product thesis.

**What happened:** The trainer gave a detailed observation about clamshells — he noticed Pranav's left side was tougher, inferred tighter adductors, suggested focusing on that. Pranav asked "would you say all that into the app?" and the trainer said no, he'd keep it short. "Too much data is bad."

Pranav pushed: "But why do you care about keeping it short?" The trainer couldn't really answer. So Pranav asked the real question: "Is it because you think more data isn't useful? Or because you're just used to the constraints of writing, where you physically can't capture everything, so you've trained yourself to not even think about it?"

The trainer realized: **it's the second one.** He's not keeping it short because brevity is better — he's keeping it short because he's never had a world where capturing everything was possible. Writing is slow, memory is limited, so trainers self-censor. They stop even *thinking* about all the information exchanged during a session because they've internalized that it can't be captured.

**The insight:** This isn't a market where trainers have a burning problem and are looking for a solution. The baseline is so low that **trainers don't even have awareness of how much better they could be.** There's no sense that "so much more can be done" — because nothing like this exists. The trainer didn't walk in wanting this tool. But by the end of the session, after seeing what's possible, he said it would be very helpful *if it works the way he'd want it to.*

**The unlock is convenience.** The trainer said explicitly: "It all depends on how convenient it is for me." Two things are true:
1. Trainers don't understand how much more an AI could help them — because the possibility has never existed.
2. They would actually talk more and record far more than they currently write — IF it's convenient enough. The friction of writing is what caps the information, not the trainer's willingness.

**What this means for the product:** We're not solving a known pain point. We're creating a new capability that trainers don't know they need until they see it work. That means:
- The product has to be so frictionless that trainers use it without changing their workflow much
- The value has to be demonstrated, not explained — they have to feel it
- The first experience matters enormously — if clip recording is clunky or the output is wrong, they'll dismiss it as "not worth it"
- Once they start capturing more, and the Brain starts surfacing insights from that data, THAT's when the real hook lands
