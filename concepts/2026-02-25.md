# Day 3 — Feb 25, 2026 (Phase 1b: Intent Classification + Session Context)

## Context Window Management for LLMs

When you give Claude a task, everything it sees — system prompt, tools, user message — is one continuous "context window." The question is: where does each piece of information belong?

**System prompt = behavior rules (static).** "You are a parser. Here are 15 rules." This doesn't change between requests. It defines *how* to behave.

**User message = per-request data (dynamic).** "Here's the session context. Here's the transcript." This changes every clip. It defines *what* to process.

Mixing them is a common mistake in AI engineering. If you put dynamic data in the system prompt, you're blurring "how to behave" with "what to process." Keeping them separate means the system prompt stays stable and testable, and the user message is the only thing that varies.

This is the same principle as separating configuration from input in regular software. The system prompt is config. The user message is input.

## Intent Classification Through Tool Design

Instead of building a separate classifier ("is this a new exercise or a modification?"), we encode intent directly in the tool choices:

- `record_exercise_card` → "this is new"
- `record_observation_card` → "this is an observation"
- `modify_exercise_card` → "this updates something that exists"

Claude picks the right tool based on context. The tool name IS the classification. No separate step needed.

This is cleaner than a two-step approach (classify first, then extract) for three reasons:
1. **One API call, not two.** Fewer round-trips, lower latency.
2. **Classification and extraction happen together.** Claude sees the transcript + context and simultaneously decides what it is AND extracts the data. The two tasks inform each other.
3. **The classification is implicit in the output.** You don't need to parse a separate "intent" field — the tool choice tells you.

The limit: this works when intents map cleanly to different output shapes. Exercise cards, observations, and modifications all have different fields. If two intents had identical schemas, you'd need to differentiate them some other way.

## Giving an LLM Memory (Session Context)

Our parser originally saw each voice clip in isolation. The trainer says "RPE 8 on those" and the parser has no idea what "those" refers to.

The fix: send prior session entries alongside each new transcript. The phone keeps the full session state and sends it with every clip (stateless server). We format prior entries as numbered readable text:

```
Session context (2 entries logged so far):
[1] Exercise: bench press | Sets: 3x10 reps @ 80kg
[2] Observation: Client seemed fatigued (yellow flag)

New transcript to parse:
RPE 8 on those
```

The numbered IDs (`[1]`, `[2]`) are the key design choice. They give Claude an unambiguous way to reference existing entries. When it calls `modify_exercise_card` with `target_entry_id: 1`, there's no ambiguity about which entry it means.

The format matters: structured readable text (not raw JSON, not narrative prose). It's compact enough to not waste tokens, readable enough for Claude to understand naturally, and has clear identifiers for targeting.

## Evolving an AI System Without Breaking It

Day 2 built a parser with 2 tools and 10 rules. Day 3 added a third tool and 5 more rules. The key discipline: **backward compatibility.**

- `parse_transcript("bench 10 reps")` still works identically — no context, no modifications, same as Day 2.
- `session_context` is optional. Omit it and the behavior is unchanged.
- `ParserResult.modifications` defaults to an empty tuple. Existing code that only checks `exercise_cards` and `observation_cards` isn't affected.
- All 30 original tests still pass without modification.

This is the same principle as evolving an API: new features are additive, defaults preserve old behavior, nothing breaks for existing callers.

## The "Add" vs "Correct" Distinction

When the trainer says "also, RPE 8 on those" — that's adding new information (RPE wasn't recorded before). When they say "no wait, 85 not 80" — that's correcting existing information.

These look similar but have different downstream behavior:
- **Add** = layer new data on top. Don't touch existing fields. The bench press had 3 sets with reps and weight. Now it also has RPE. Nothing was removed.
- **Correct** = overwrite specific fields. The weight was 80, now it's 85. The old value is replaced.

The parser distinguishes them with the `action` field. The default is always "add" — correction requires explicit trainer signal ("no wait", "actually", "I meant"). This makes the system safe by default: it won't overwrite data unless the trainer clearly intends it.

## Product Principle: Observation Cards Are the Trainer's Words

When the parser encounters ambiguity (e.g., two bench press entries and the trainer says "RPE 8 on bench"), it needs to say "I couldn't resolve this." The initial instinct was to create a yellow-flag observation card.

But observation cards are the trainer's actual notes — what they saw, what they said. Putting system-generated ambiguity notices in the observation stream pollutes the trainer's data. It's the wrong container.

The cleaner approach: the endpoint layer separates these. The API response includes a `clarifications_needed` field for unresolved items. The mobile app shows these as dismissable prompts ("Did you mean bench press or incline bench?"). The trainer taps one, and the modification gets applied. Ambiguity never touches the observation stream.

General principle: every piece of data in the session timeline should be something the trainer actually said or observed. System concerns get their own channel.
