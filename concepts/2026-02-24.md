# Day 2 — Feb 24, 2026 (Phase 1b: Claude Parser + Tool Use)

## How Claude Works — The One-Sentence Version

Claude reads text and writes text. That's the entire thing. Every technique we use (tool use, RAG, fine-tuning, system prompts) is just about changing **what goes in** or **how the output is structured**. The model itself always does the same thing: reads everything you give it, generates a response token by token.

## Token-by-Token Generation

Claude doesn't think about the whole response and then write it. It generates one **token** (roughly a word or word-piece) at a time. Each token is chosen based on everything that came before it — the system prompt, the tools, the user message, and all the tokens it's already generated. There's no separate "planning" step. The response emerges one token at a time.

This matters because it means Claude's "decisions" aren't separate from its "writing." When it picks which tool to call, that's not a classification step followed by a form-filling step — it's all one continuous generation. The tool name tokens come first, then the input field tokens, each influenced by everything before it.

## Tool Use (What We're Building Today)

Tool use = giving Claude structured forms to fill in instead of letting it write freeform text.

You define **tools** with three parts:
- **`name`** — like a function name: `record_exercise_card`
- **`description`** — tells Claude when to use it: "Record a structured exercise card from trainer speech"
- **`input_schema`** — JSON Schema defining the fields, types, and required fields

Claude's response comes back as structured data guaranteed to match the schema:
```json
{
  "type": "tool_use",
  "name": "record_exercise_card",
  "input": {
    "exercise_name": "bench press",
    "sets": [{"reps": 10, "weight": 80, "weight_unit": "kg"}],
    "form_notes": ["good depth"]
  }
}
```

No regex parsing. No hoping Claude formats things right. The API guarantees the structure.

**`tool_choice: {"type": "any"}`** — Forces Claude to call at least one tool. Without this, Claude might just write a text response like "The trainer did bench press..." which is useless for us.

## Why Two Tools Instead of One

We use `record_exercise_card` and `record_observation_card` as separate tools. The tool **name IS the classification** — when Claude picks which tool to call, it's simultaneously deciding "is this an exercise or an observation?" Two separate schemas also prevent weird states like an observation card accidentally having `sets` data. Clean types, no cross-contamination.

## How Claude Decides Which Tool to Call

Same way it decides anything — language comprehension through token prediction. It reads:
1. The tool names and descriptions
2. The field names in each schema
3. The transcript

"Bench press 3 sets of 10" → the word "exercise" in the tool name, the `sets` field, the `exercise_name` field — everything points to `record_exercise_card`.

"Marcus seems fatigued today" → no exercise, no sets → `record_observation_card` fits.

It's not a rule engine. It's the same language understanding Claude uses for everything, guided by well-named tools and well-described fields. Good naming in the schema = good classification.

A single transcript can produce **multiple tool calls** — "Bench press 3x10, also Marcus's knee is bothering him" → one `record_exercise_card` + one `record_observation_card`.

## The Unified Map: How "One Brain" Becomes Many Capabilities

Claude is one model that reads and writes text. Every technique is just a different way of using that:

| Technique | What it does | Analogy | Where in our project |
|-----------|-------------|---------|---------------------|
| **System prompt** | A sticky note on the desk: "You are a gym transcript parser. Follow these rules." Shapes behavior — but it's just text Claude reads. | Instructions for a worker | Parser (Day 2), Brain (Phase 3) |
| **Tool use** | Hand Claude specific forms to fill in instead of letting it write freeform. Same brain, structured output. | Giving someone forms vs. blank paper | Parser (Day 2) — transcript → structured cards |
| **RAG** | Before asking Claude a question, go to a filing cabinet, pull out relevant files, put them on the desk. Same brain, more information to work with. | Giving someone reference documents | The Brain (Phase 3) — "How's Marcus's squat?" + retrieved session history |
| **Fine-tuning** | Send the model to a specialized training course. Its brain actually changes. Heavy, expensive, rarely needed. | Specialized education | Probably never in this project |
| **Embeddings** | Not Claude at all — a separate, smaller model that turns text into numbers so you can search for similar things. Used to find relevant documents *before* handing them to Claude (the "retrieval" part of RAG). | An index/search engine | Phase 3 — finding relevant client data |

The map of our voice pipeline:
```
Trainer speaks
    ↓
Deepgram (NOT Claude — separate service, turns audio → text)
    ↓
Claude + tool_use (today — transcript → structured cards)
    ↓
Validation layer (NOT Claude — deterministic code, fuzzy matching, unit conversion)
    ↓
Database (structured SessionEntry records)
```

Every time Claude shows up in this project, it's the same model doing the same thing — reading text, writing text. We're just changing what we put on the desk and what forms we give it.

## Where Does Vertical AI Moat Actually Come From?

The instinct says: "Fine-tune a model on fitness data, and now you have something nobody else has." But fine-tuning is a marginal improvement on one step of the pipeline — maybe Claude parses gym speech 95% instead of 88%. That's not a moat. The next model generation might make your fine-tuning obsolete overnight.

**What actually makes vertical AI defensible:**

The **system**, not the model. Claude is a commodity — anyone can call the API. The intelligence is in how you use it:

- **The data model.** `SessionEntry` with exercise cards and observation cards, designed around how trainers actually think and speak. Not a generic "fitness log" — a structure that reflects real training workflows, built over weeks of iteration.
- **The tool schema.** Which fields exist, what's required vs optional, how sets expand, what gets preserved vs normalized. Every decision encodes domain understanding.
- **The system prompt.** 10 rules tuned on real trainer speech patterns. Weeks of testing and iteration to get right.
- **The exercise database.** 142 exercises, 3,466 aliases, expert-level common errors. Hand-researched domain knowledge.
- **The validation layer.** Fuzzy matching thresholds tuned for gym vocabulary. Unit conversion. Pain extraction. Domain-specific post-processing that no general-purpose tool would build.
- **Accumulated client data.** Once a trainer uses the system for 3 months, their entire client history lives here. They can't leave without losing everything. This is the real lock-in.
- **The full workflow.** Voice → transcription → parsing → validation → session timeline → briefings → pattern detection → The Brain. Each piece feeds the next. Replicating one step doesn't replicate the system.

**Could Claude/Anthropic ship "Claude for Fitness" and eat this?** They'd have a general-purpose model that knows what a bench press is. Same starting point we have today. They wouldn't have the data model, the workflow, the accumulated trainer data, the domain-tuned prompts, or the validation logic. Building that requires understanding the domain deeply — which is exactly what we're doing.

**When fine-tuning might matter (later):** Once thousands of real transcripts flow through the system, fine-tuning could help with weird speech patterns, reduce latency, or cut API costs. But that's an optimization on top of a working system — not the foundation. And it requires real data we don't have yet. Build the system first, collect data, then consider fine-tuning.

## Why Claude Can Do a Task It's Never Seen Before

SuperTrainer doesn't exist yet. Apps like it barely exist. No one has built "trainer voice note → structured exercise card" before, so there's no dataset of this exact task on the internet. So how can Claude do it?

Because **Claude hasn't done this specific task, but it's done every piece of it separately:**

1. **Understand spoken English about exercise.** Claude has read millions of fitness forum posts, training articles, Reddit threads where people say "did 3 sets of 10 at 80kg on bench." It knows the language of the gym.

2. **Extract structured data from unstructured text.** This is one of the most common things language models do — across every domain. Medical records → structured fields. Legal contracts → key terms. Recipes → ingredient lists. The *pattern* of "read messy text, pull out specific fields" is deeply familiar.

3. **Fill in a JSON schema via tool_use.** Claude was specifically trained on this. It's seen millions of examples of "here's a schema, here's some text, fill in the form."

Our task is **novel as a combination** but **familiar in every component.** We're combining three things Claude already knows how to do: understanding gym language + extracting structured data from text + filling in tool schemas.

This is the insight behind tool_use as a design pattern: you don't need the model to have seen your exact task. You need:
- The model understands the **domain language** (fitness — yes)
- The model understands the **task pattern** (text → structured data — yes)
- You provide a **good schema** that tells it exactly what output you want

The schema is the bridge between "Claude knows fitness" and "Claude fills in our specific SessionEntry format." Claude doesn't need to know what SuperTrainer is. It just needs: "here's a transcript about exercise, here are two forms, fill in the right one." The intelligence about *what fields matter for a training session* — that comes from us. From the schema we designed. From the data model we built. That's where the domain expertise lives — in the system, not the model.

## Real Trainer Insight: Terse vs. Verbose Speech Patterns

From talking to a real trainer (Pranav's own): trainers and clients record information very differently.

**Trainer mode (terse):** "Second set, bench press, 80 pounds, three sets." No filler. No context. Just the data. They've been doing this for years — they know what matters and say only that.

**Client mode (verbose):** "So I just did bench press and I think I did like 3 sets of 10? The weight felt kind of heavy, like 80 pounds, and my shoulder was a bit sore on the last couple reps." Filler words, hedging ("I think", "kind of"), mixed data and feelings.

**Why this matters for the parser:**
- We're building for trainers first (the PRD). But even trainers sometimes add quick observations ("good depth", "complained about knee pain").
- **Terse input is actually harder to parse.** Fewer words = less context to disambiguate. "Second set, three sets bench press, 80" — is "second set" a reference to a previous exercise?
- The system prompt and schema need to handle both extremes gracefully. Day 6 (real transcript testing) is where we'll tune for actual speech patterns.
- This validates the observation card design — trainers won't ramble about pain. They'll be precise: "knee pain on last rep." Short, flagged, specific. Exactly what the observation card captures.

## Per-Clip Processing: How the Trainer Actually Uses This

The trainer records **one audio clip at a time**. Press record, say something, stop. Each clip is sent to the server and parsed independently.

Two recording styles exist:

**Style A — one clip per set (terse, incremental):**
- Clip 1: "Bench press, first set, 10 reps at 80 kg"
- Clip 2: "Second set done, same weight"
- Clip 3: "Third set, bumped up to 85"

**Style B — one clip per exercise (batched):**
- Clip 1: "Bench press, 3 sets of 10 at 80 kg, good form throughout"

Both are valid. Day 2 handles Style B (everything in one clip). Day 3 adds session context for Style A — the phone sends previous entries along with each new clip, so Claude can resolve "same weight" and "second set."

The data hierarchy from the schema:
```
Exercise Card: "bench press"          ← the big box
├── Set 1: {reps: 10, weight: 80}    ← small boxes inside
├── Set 2: {reps: 10, weight: 80}
└── Set 3: {reps: 10, weight: 80}
```

**The trainer does NOT need to optimize their speech for the app.** "First exercise bench press" works. "Bench, 3 by 10 at 80" works. "Did some bench pressing, about 3 sets" works. That's the whole point of using Claude — it handles natural language variation. The app is smart enough to catch it.

## Frozen Dataclasses vs. User Editing (Code Concerns ≠ UX Concerns)

The parser's output objects are "frozen" (immutable in code). This is a **programmer safety net** — it means our own code can't accidentally modify the parsed data between when Claude produces it and when it gets saved to the database.

This has nothing to do with the trainer's ability to edit. The full flow:

1. Trainer speaks → parser creates frozen `ParsedExerciseCard`
2. Data gets saved to database as a `SessionEntry` row
3. Card appears on trainer's phone screen
4. If wrong → trainer taps, edits the field, saves → hits `PATCH /entries/{id}` → database updated

The backend already supports full editing (built in Phase 1a, Day 4). The frozen dataclass protects the parser's output from code bugs. The trainer has full control over the final data.

**Key UX insight:** editing must be extremely smooth. The trainer is mid-session with a client — they can't spend 30 seconds fixing a wrong rep count. See card, tap wrong field, type correct number, done. One or two taps. This is a mobile design concern (Phase 2) but the backend already supports it.

## What Claude Brings vs. What We Bring (The Intelligence Split)

A recurring pattern in tool_use: the intelligence is split between the model and the schema.

**Example: flag_color on observation cards.** The schema defines three severity levels:
- Red: pain, injury, safety concern
- Yellow: something to watch (fatigue, minor discomfort)
- Green: positive note (PR, milestone)

Claude already understands that "sharp knee pain" is more serious than "seemed tired today." That's general language comprehension from training. But Claude doesn't know that *our system* uses red/yellow/green, or that we consider fatigue "yellow" and pain "red."

The split:
- **Claude brings:** language understanding, severity comprehension, context
- **We bring:** the specific framework (red/yellow/green), what each level means in our domain, the rules for when to use each

Neither is enough alone. Claude without our schema would know "knee pain is bad" but not how to categorize it. Our schema without Claude would be an empty form nobody can fill in.

**This is the pattern for all tool_use design.** For every field, ask: "What does Claude already know how to do?" and "What do we need to tell it?" Put the domain-specific structure in the schema descriptions. Let Claude handle the language comprehension.

**And the best part:** if the trainer later says "fatigue should be red, not yellow — I consider it a serious sign" — we change one string in the description. No retraining, no fine-tuning. The schema IS the configuration.

## Testing External AI Services: The Mocking Pattern

When your code calls an external API (Claude, Deepgram, Stripe, anything), you can't call the real API in tests. It's slow, costs money, and the responses aren't deterministic. So you **mock** it — you fake the API response so you can test that *your code* handles different response shapes correctly.

**The mental model:** You're not testing whether Claude parses correctly (that's Anthropic's job). You're testing whether **your code** correctly:
- Rejects bad input before making the API call
- Converts the API's response format into your data structures
- Handles every field (including optional ones that might be missing)
- Handles edge cases (empty responses, unexpected formats)
- Passes the right arguments to the API (correct model, correct parameters)

**How it works in practice:**

1. Use `@patch` to replace the real API client with a fake
2. Build `MagicMock` objects that look like the API's response — same attributes, same structure
3. Your code doesn't know it's talking to a fake. It processes the mock response the same way it would process a real one
4. You assert that your code produced the correct output from the mocked input

**Example flow for the parser:**
```
Mock: Claude returns [{"type": "tool_use", "name": "record_exercise_card", "input": {"exercise_name": "bench press", "sets": [...]}}]
Test: Does our code correctly convert that into a ParsedExerciseCard with the right fields?
```

**This pattern is the same everywhere.** We used it for Deepgram (Day 1) and Claude (Day 2). Any time you integrate an external service, you mock the service boundary and test your wrapper logic. The tests are fast (no network calls), free (no API costs), and deterministic (same mock = same result every time).

**What we're NOT testing with mocks:** Whether Claude actually produces good output for real transcripts. That's Day 6 — real transcript testing with the actual API. Mocks test our code; real tests test the AI.
